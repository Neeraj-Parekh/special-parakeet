Top-3 specific design decisions worth flagging to the orchestrator:

1. **The FOR UPDATE lock spans the Python cap-checks, not just the SQL read.** The prior C8 fix-aspirational-comment in alembic 003 said "the verify path will hold the lock across cap-checks" but that's impossible with the split-txn design — the read txn commits before the cap-checks run, releasing any lock. My fix uses a `_DbCounterTxn` handle that holds an OPEN transaction across the Python cap-checks (inactivity, per-txn, monthly, device_id, user_id, cooling 24h) and only commits/rolls-back at the end. This means a slow Python cap-check (e.g. device_id list iteration on a 5-device mandate) holds the lock longer — but that's the CORRECT trade-off: the lock must span the cap-check + write or the race condition returns. The lock is per-mandate (keyed by mandate_sub), NOT global, so concurrent verifies on DIFFERENT mandates don't block each other. Only concurrent verifies on the SAME mandate serialize — which is exactly the safety property we want (two simultaneous transactions against the same customer's ₹15k cap should serialize).

2. **C9 reset has a "back-fill without reset" sub-branch for the migration just-landed case.** When alembic 004 lands, existing `mandate_counters` rows have `month_key = ''` (the DEFAULT). If my C9 reset unconditionally ran `cumulative_monthly = 0` whenever `stored_month_key != current_month_key`, the FIRST verify_mandate call after the migration would reset EVERY existing counter to 0 — losing months of legitimate cumulative spend tracking. Instead, the C9 reset has TWO branches: (a) `stored_month_key` is non-empty AND differs from current → reset (the month genuinely rolled over); (b) `stored_month_key` is empty (the migration just landed) → back-fill `month_key = current_month_key` WITHOUT resetting cumulative_monthly (preserves the legacy value; lets the next genuine month rollover trigger the reset on its own). The pragmatic choice is "don't lose data on the migration cutover; let the next real month-boundary do the reset." Tests cover both branches (the source-grep test asserts the `stored_month_key` variable; the DB-path test_c9_month_reset_under_postgres inserts a row with `month_key='2025-12'` (non-empty + stale) which triggers branch (a)).

3. **C10 prune runs on EVERY counter-event INSERT (inline prune-on-write), NOT on a 1% probabilistic schedule.** The original alembic 003 docstring said "the verify path prunes rows older than 24h on read so the table stays bounded under steady-state traffic; the cleanup is probabilistic (1% of verifies)". That was a code-only aspiration — the probabilistic prune was NEVER actually implemented (no `if random.random() < 0.01: cur.execute("DELETE...")` anywhere). My fix runs the prune DELETE on EVERY counter-event INSERT inside the same transaction. This is slightly more expensive per-write (one extra DELETE per VALID verify), but: (a) the new `ix_mandate_counter_events_created_at` index makes the DELETE a fast range scan (touches only the rows being deleted, ~1/365 of the table per day under steady-state); (b) the inline prune is provably-bounded — there's no chance of a "scheduler didn't run" runaway-table scenario; (c) no scheduler dependency (simpler ops story). The 90-day retention is generous headroom over the 24h cooling window's needs — 90 days gives compliance audit export a comfortable lookback window while keeping the table at ~3 months of events (a far cry from unbounded growth). The 14-day scheduler-based prune would be slightly cheaper per-write but adds a scheduler dep + a runaway risk if the scheduler fails — the inline-on-write choice trades a small per-write cost for provable boundedness.

Top-3 specific design decisions worth flagging to the orchestrator:

1. **The nonce is NOT part of the HMAC canonical_body — by design.** The T1.1 HMAC chain `signature_2 = HMAC(admin2_key, signature_1 || canonical_body || timestamp)` is UNCHANGED from Subagent 11-routes — `canonical_body = json.dumps({"prediction_id": prediction_id, "decision": decision, "notes": payload.notes}, sort_keys=True)`. The A2 fix adds the nonce as a SEPARATE one-shot replay-defense field that runs BEFORE the HMAC chain verification (cheaper pre-filter — a replayed request short-circuits before recomputing the admin2-key iteration). This means a captured request can be replayed ONLY if the attacker mutates the nonce (which would invalidate the audit trail's nonce-hash binding) OR keeps the same nonce (which the server rejects with 409). The HMAC chain is unaffected — Subagent 11-routes's T1.1 fix is preserved verbatim; only the key passed to HMAC is HKDF-derived (the A1 fix).

2. **The override_nonces table stores the SHA-256 HASH of the nonce, NOT the raw nonce — defense in depth.** Same redaction posture as `redact_customer()` in src/audit/logger.py — the raw nonce is only meaningful in transit (the client generated it fresh for THIS request); storing the hash means a DB compromise (SQL injection, backup leak) doesn't reveal the raw nonce values that could be used to forge future requests. The nonce_hash is computed via `hashlib.sha256(payload.nonce.encode()).hexdigest()` BEFORE the `_check_and_consume_override_nonce` call — the raw nonce string never leaves the request-handling process. The audit log ALSO stores `override_nonce_hash` (NOT the raw nonce) so the audit trail can prove "this request was a fresh sighting, not a replay" without leaking the raw nonce value.

3. **The `nonce` field is REQUIRED on OverrideIn — not optional.** This means every existing T1.1 dual-control test had to be updated to send a fresh nonce field (4 of the 5 dual-control tests in test_v3_endpoints.py — the 5th uses the legacy query-param form which bypasses OverrideIn entirely). The task spec said "the existing T1.1 dual-control test STILL PASSES — you're extending T1.1, not breaking it" — I interpreted "STILL PASSES" as "the semantic assertion (HMAC chain works + audit stores the verified fields) still holds" — not "the test code is unchanged". The test updates are minimal (each test adds one `"nonce": _fresh_nonce()` line to the JSON body, and `test_dual_control_two_different_keys_succeeds` adds 6 lines for the HKDF client-side derivation); the assertions are preserved verbatim with 2 new lines asserting the new `override_nonce_hash` field. The autouse fixture clears the in-memory LRU + HKDF cache between tests so test-order-dependence is eliminated.
