Top-3 specific design decisions worth flagging to the orchestrator:

1. **The merchant_id binding's authoritative source is the api_keys table (alembic 007) in Postgres mode + the RTO_KEY_MERCHANT_BINDINGS env var in file mode — both paths share the get_key_merchant_id() helper.** The file-mode path is what tests/test_tenant_isolation.py exercises (env-var CSV of key:merchant_id pairs). The Postgres-mode path is forward-compat (the api_keys table is created by migration 007 but the lookup logic in get_key_merchant_id() currently only consults the env-var file-mode path — the DB-backed lookup is deferred to a future routes.py change once key-creation tooling lands). The shape parity means the file-mode → Postgres-mode upgrade path is a single helper swap (no handler rewrites). Legacy keys (the default score-demo-key / admin-demo-key in default_keys()) are unbound → get_key_merchant_id returns None → no isolation enforced → existing tests pass without binding setup. The 117 pre-F19 tests don't set RTO_KEY_MERCHANT_BINDINGS → no isolation → no regression.

2. **Cross-tenant access produces DIFFERENT HTTP statuses depending on the access pattern — by design.** A caller-supplied merchant_id that mismatches the caller's bound merchant_id (e.g. merch A scorer submitting OrderIn.merchant_id=merch_b, or merch A admin querying /v1/usage?merchant_id=merch_b) → 403 "cross-tenant access denied" (the caller tried to access another tenant's data; the explicit mismatch deserves an explicit denial). A lookup-based cross-tenant access (e.g. merch A admin looking up merch B's audit_id via /audit/{audit_id} or /v1/audit/{audit_id}/proof) → 404 "audit record not found" (the cross-tenant existence is masked — the caller can't tell whether the audit_id belongs to another merchant or simply doesn't exist). A filtered-tail cross-tenant access (e.g. merch A scorer asking /v1/explain/shap?order_id=<merch B's order_id>) → 422 "no past prediction found" (the audit tail filter silently excludes merch B's records; the lookup misses + the same generic 422 fires). This 3-tier posture (403 for explicit mismatches, 404 for lookup-based, 422 for filter-based) follows the multi-tenant isolation best-practice of "fail closed + don't leak cross-tenant existence".

3. **The X-Mandate-Scope header is parsed but IGNORED for enforcement — the bound scope from the API key is the only authority (D13 fix).** The previous behavior was the D13 finding: a scorer-scope key could send X-Mandate-Scope: admin + X-Agent-Action: override to escalate to admin authority. The fix: enforce_agent_action now extracts the caller's bound key scope via get_key_scope(token, scorer_keys, admin_keys) + passes it to check_agent_action(action, key_scope=...) which consults SCOPE_ACTION_MAP[key_scope] to verify the action is permitted for the caller's scope. The X-Mandate-Scope header is still parsed (for forward-compat with future per-mandate-scope allowlist policies) but NEVER consulted for enforcement. The test_d13_scorer_cannot_override_via_x_agent_action test verifies this by sending X-Mandate-Scope: admin with a scorer key + asserting the 403 scope-mismatch message fires (the bound scope wins, not the client-supplied header).
