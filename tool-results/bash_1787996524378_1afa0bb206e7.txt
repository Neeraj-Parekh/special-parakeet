Attack Vector 1: Model Extraction (Tramer et al., USENIX Security 2016)

The attack: Query your `/risk/score` API thousands of times with crafted inputs. Reconstruct your model's decision boundary. Build a surrogate model. Use it to find adversarial inputs that evade detection.

- No query perturbation defense (your model returns exact probabilities, not binned scores).
- No model fingerprinting (no watermark in predictions).

The paper: Tramer et al., "Stealing Machine Learning Models via Prediction APIs", USENIX Security 2016 . They extracted a model with 100x fewer queries than training data by using equation-solving on the decision boundary.

Your defense:
1. Return binned scores, not exact probabilities. Instead of `probability: 0.7341`, return `probability: 0.73` (2 decimal bins). Increases extraction error by 10-100x.
2. Add Gaussian noise to probabilities. `proba += np.random.normal(0, 0.01)`. Tramer shows this increases extraction queries by 5-10x.
3. Rate limit per-merchant + per-IP. Your TokenBucket is per-client. Add per-IP bucketing.
4. Model watermarking. Embed a secret trigger pattern in training data. If a surrogate model reproduces the trigger, you detect extraction.

Attack Vector 2: Input Perturbation / Evasion

The attack: Modify order features slightly to flip the decision from REJECT to ACCEPT. E.g., change `address_quality` from "vague" to "complete" (add a landmark), reduce `amount_inr` by ₹1 to slip under a threshold.

Your vulnerability:
- Your rules engine uses hard thresholds (`amount > 50000`). Gradient-free attacks can binary-search the threshold in 17 queries (log₂(50,000)).
- Your SHAP explainer leaks which features matter most — attackers prioritize perturbing high-SHAP features.

The paper: "Adversarial Attacks and Defenses in Machine Learning for Tabular Data" (IEEE Access, 2024) . Tabular data is MORE vulnerable than images because feature semantics are interpretable — attackers know exactly what to change.

Your defense:
1. Randomized thresholds. Instead of `amount > 50000`, use `amount > 50000 + random.uniform(-500, 500)`. Attackers cannot binary-search a moving target.
2. Feature consistency checks. If `address_quality` changes from "vague" to "complete" but `address_length` doesn't increase by >10 chars, flag as adversarial.
3. Ensemble disagreement. Run 3 models (Amazon, Olist, a random forest). If they disagree by >0.2 on probability, flag for manual review.

Attack Vector 3: Replay / Session Hijacking

The attack: Capture a valid `Idempotency-Key` + `Bearer` token. Replay the same request to drain the merchant's rate limit or generate duplicate audit records.

Your vulnerability:
- Your idempotency key expires but the TTL is not enforced in Redis (only in Postgres).
- Your `X-Agent-Action` header is parsed but the scope enforcement happens AFTER auth — a leaked admin key can declare any action.

Your defense:
1. HMAC-SHA256 on every request body. `signature = HMAC(secret, method + path + body + timestamp)`. Server verifies before processing. Replays fail because timestamp is stale.
2. Short-lived tokens. Your API keys are static. Razorpay uses JWT with 5-minute expiry + refresh tokens.

Attack Vector 4: Denial of Service via Feature Store

The attack: Flood `/risk/score` with unique `customer_id`s. Each miss in Redis triggers a PostgreSQL query. Postgres connection pool exhausts. System 500s.

Your vulnerability:
- Your `FeatureStore.get_online_features` does a Redis pipeline but falls back to PostgreSQL on miss. No circuit breaker on the PG fallback.
- Your `TokenBucket` is in-memory per-process. In a multi-worker setup, each worker has its own bucket — a 1000 req/s attack spread across 4 workers hits 4000 req/s total.

Your defense:
1. Cache-aside with negative caching. If `customer_id` not in Redis, cache a "null" value for 60s. Prevents PG query storms.
2. Distributed rate limiting. Replace in-memory TokenBucket with Redis-backed sliding window (`SLIDE-RATE-LIMIT` pattern).
3. Connection pool monitoring. Alert when PG pool utilization >80%. Auto-scale workers or reject new connections.

The attack: Compromise the API container. Modify `audit_records` table directly. The hash chain breaks, but if the attacker also modifies `prev_hash`, the chain re-computes as valid.

Your vulnerability:
- Your `raw_hash` includes `prev_hash` but both are in the same PostgreSQL row. A DB admin with `UPDATE` access can rewrite history.
- No external witness (separate signing key, WORM storage, blockchain anchor).

Your defense:
1. Separate signing key. The `raw_hash` should be `HMAC(signing_key, canonical(body) + prev_hash)`. The signing key lives in a Hardware Security Module (HSM) or AWS KMS — never in the app container.
2. Periodic blockchain anchor. Every hour, write the latest Merkle root to a public blockchain (Ethereum, Bitcoin). Tampering requires rewriting blockchain history — computationally infeasible.
3. Write-Once-Read-Many (WORM) storage. Export audit records to S3 Glacier with WORM policy. 7-year retention. Cannot be deleted or modified.
