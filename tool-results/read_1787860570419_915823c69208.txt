   184→  2383→1. **The merchant_id binding's authoritative source is the api_keys table (alembic 007) in Postgres mode + the RTO_KEY_MERCHANT_BINDINGS env var in file mode — both paths share the get_key_merchant_id() helper.** The file-mode path is what tests/test_tenant_isolation.py exercises (env-var CSV of key:merchant_id pairs).    185→  2384→
   186→  2385→2. **Cross-tenant access produces DIFFERENT HTTP statuses depending on the access pattern — by design.** A caller-supplied merchant_id that mismatches the caller's bound merchant_id (e.g. merch A scorer submitting OrderIn.merchant_id=merch_b, or merch A admin querying /v1/usage?merchant_id=merch_b) → 403 "cross-tenant access denied" (the caller tried to access another tenant's data; the explicit mismatch deserves an explicit denial). A lookup-based cross-tenant access (e.g. merch A admin looking up merch B's audit_id via /audit/{audit_id} or /v1/audit/{audit_id}/proof) → 404 "audit record not found" (the cross-tenant existence is masked — the caller can't tell whether the audit_id belongs to another merchant or simply doesn't exist). A filtered-tail cross-tenant access (e.g. merch A scorer asking /v1/explain/shap?order_id=<merch B's order_id>) → 422 "no past prediction found" (the audit tail filter silently excludes merch B's records; the lookup misses + the same generic 422 fires). This 3-tier posture (403 for explicit mismatches, 404 for lookup-based, 422 for filter-based) follows the multi-tenant isolation best-practice of "fail closed + don't leak cross-tenant existence".
   187→  2386→
   188→  2387→3. **The X-Mandate-Scope header is parsed but IGNORED for enforcement — the bound scope from the API key is the only authority (D13 fix).** The previous behavior was the D13 finding: a scorer-scope key could send X-Mandate-Scope: admin + X-Agent-Action: override to escalate to admin authority.
