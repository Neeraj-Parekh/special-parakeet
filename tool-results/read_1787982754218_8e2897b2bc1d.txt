   134→   134→   134→Attack Vector 1: Model Extraction (Tramer et al., USENIX Security 2016)
   135→   135→   135→
   136→   136→   136→The attack: Query your `/risk/score` API thousands of times with crafted inputs. Reconstruct your model's decision boundary. Build a surrogate model. Use it to find adversarial inputs that evade detection.
   137→   137→   137→
   138→   138→   138→Your vulnerability:
   139→   139→   139→- No rate limiting per-merchant on the score endpoint (your TokenBucket exists but `tests/test_security.py` only tests 8 cases — no adversarial load pattern).
   140→   140→   140→- No query perturbation defense (your model returns exact probabilities, not binned scores).
   141→   141→   141→- No model fingerprinting (no watermark in predictions).
   142→   142→   142→
   143→   143→   143→The paper: Tramer et al., "Stealing Machine Learning Models via Prediction APIs", USENIX Security 2016 . They extracted a model with 100x fewer queries than training data by using equation-solving on the decision boundary.
   144→   144→   144→
   145→   145→   145→Your defense:
   146→   146→   146→1. Return binned scores, not exact probabilities. Instead of `probability: 0.7341`, return `probability: 0.73` (2 decimal bins). Increases extraction error by 10-100x.
   147→   147→   147→2. Add Gaussian noise to probabilities. `proba += np.random.normal(0, 0.01)`. Tramer shows this increases extraction queries by 5-10x.
   148→   148→   148→3. Rate limit per-merchant + per-IP. Your TokenBucket is per-client. Add per-IP bucketing.
   149→   149→   149→4. Model watermarking. Embed a secret trigger pattern in training data. If a surrogate model reproduces the trigger, you detect extraction.
   150→   150→   150→
   151→   151→   151→Attack Vector 2: Input Perturbation / Evasion
   152→   152→   152→
   153→   153→   153→The attack: Modify order features slightly to flip the decision from REJECT to ACCEPT. E.g., change `address_quality` from "vague" to "complete" (add a landmark), reduce `amount_inr` by ₹1 to slip under a threshold.
   154→   154→   154→
   155→   155→   155→Your vulnerability:
   156→   156→   156→- Your rules engine uses hard thresholds (`amount > 50000`). Gradient-free attacks can binary-search the threshold in 17 queries (log₂(50,000)).
   157→   157→   157→- Your SHAP explainer leaks which features matter most — attackers prioritize perturbing high-SHAP features.
   158→   158→   158→
   159→   159→   159→The paper: "Adversarial Attacks and Defenses in Machine Learning for Tabular Data" (IEEE Access, 2024) . Tabular data is MORE vulnerable than images because feature semantics are interpretable — attackers know exactly what to change.
   160→   160→   160→
   161→   161→   161→Your defense:
   162→   162→   162→1. Randomized thresholds. Instead of `amount > 50000`, use `amount > 50000 + random.uniform(-500, 500)`. Attackers cannot binary-search a moving target.
   163→   163→   163→2. Feature consistency checks. If `address_quality` changes from "vague" to "complete" but `address_length` doesn't increase by >10 chars, flag as adversarial.
   164→   164→   164→3. Ensemble disagreement. Run 3 models (Amazon, Olist, a random forest). If they disagree by >0.2 on probability, flag for manual review.
   165→   165→   165→
   166→   166→   166→Attack Vector 3: Replay / Session Hijacking
   167→   167→   167→
   168→   168→   168→The attack: Capture a valid `Idempotency-Key` + `Bearer` token. Replay the same request to drain the merchant's rate limit or generate duplicate audit records.
   169→   169→   169→
   170→   170→   170→Your vulnerability:
   171→   171→   171→- Your idempotency key expires but the TTL is not enforced in Redis (only in Postgres).
   172→   172→   172→- Your `X-Agent-Action` header is parsed but the scope enforcement happens AFTER auth — a leaked admin key can declare any action.
   173→   173→   173→
   174→   174→   174→Your defense:
   175→   175→   175→1. HMAC-SHA256 on every request body. `signature = HMAC(secret, method + path + body + timestamp)`. Server verifies before processing. Replays fail because timestamp is stale.
   176→   176→   176→2. Short-lived tokens. Your API keys are static. Razorpay uses JWT with 5-minute expiry + refresh tokens.
   177→   177→   177→
   178→   178→   178→Attack Vector 4: Denial of Service via Feature Store
   179→   179→   179→
   180→   180→   180→The attack: Flood `/risk/score` with unique `customer_id`s. Each miss in Redis triggers a PostgreSQL query. Postgres connection pool exhausts. System 500s.
   181→   181→   181→
   182→   182→   182→Your vulnerability:
   183→   183→   183→- Your `FeatureStore.get_online_features` does a Redis pipeline but falls back to PostgreSQL on miss. No circuit breaker on the PG fallback.
   184→   184→   184→- Your `TokenBucket` is in-memory per-process. In a multi-worker setup, each worker has its own bucket — a 1000 req/s attack spread across 4 workers hits 4000 req/s total.
   185→   185→   185→
   186→   186→   186→Your defense:
   187→   187→   187→1. Cache-aside with negative caching. If `customer_id` not in Redis, cache a "null" value for 60s. Prevents PG query storms.
   188→   188→   188→2. Distributed rate limiting. Replace in-memory TokenBucket with Redis-backed sliding window (`SLIDE-RATE-LIMIT` pattern).
   189→   189→   189→3. Connection pool monitoring. Alert when PG pool utilization >80%. Auto-scale workers or reject new connections.

   192→   192→   192→
   193→   193→   193→The attack: Compromise the API container. Modify `audit_records` table directly. The hash chain breaks, but if the attacker also modifies `prev_hash`, the chain re-computes as valid.
   194→   194→   194→
   195→   195→   195→Your vulnerability:
   196→   196→   196→- Your `raw_hash` includes `prev_hash` but both are in the same PostgreSQL row. A DB admin with `UPDATE` access can rewrite history.

   198→   198→   198→
