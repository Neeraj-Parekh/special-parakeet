   153→| **Dual-control mandate co-sign (4-layer containment)** | `src/api/routes.py:2707-3010` (`override` handler) + `src/api/mandates.py:1-1062` (mandate lifecycle) | Mao 2026 SoK §4.2 + Mirabile 2026 *Trust in human-AI collaboration in finance* — `paper studied/.cache/notes/trust-human-ai-collaboration-finance-review.md` + Lundholm 2026 CTX-envelope | **FULL** | 4-layer containment: (1) admin1 key check (`check_key(payload.admin_signature_1, "admin", state["keys"])`) — 403 on fail; (2) same-key self-approve check (`admin1 == admin2 ⇒ 400`) — preserves the SoK §4.2 "Credential and Key Management" constraint that LLM-controlled wallets cannot self-authorize; (3) replay-nonce consumption (`_check_and_consume_override_nonce`) — 409 on replay; (4) HKDF-derived HMAC chain (`canonical_body = json.dumps({prediction_id, decision, notes}, sort_keys=True)` + `chained_msg = f"{admin1}|{canonical_body}|{ts}"` + `candidate_sig = HMAC-SHA256(derived_admin2_key, chained_msg)` + `hmac.compare_digest`) — 403 on chain mismatch. The 4 layers mean a single-admin compromise cannot forge an override: admin1's key alone is useless (no admin2 key to compute the HMAC); admin2's key alone is useless (no admin1 signature to chain on).    182→(§5.4) and lists 5 layers — but each layer is recommended IN ISOLATION, and

   204→The Ayomide 2026 SSRN *Liability for Autonomous Financial Agents* paper's
   205→Embedded Legality 5 mandates (§6.5: kill-switch endpoint, tamper-evident
   206→append-only log within 24h, transaction value limits per-tx/per-window/
   207→per-net-position, jurisdictional anchoring, 48h/10-day interpretability
   208→timelines) are ALL satisfied by layers 3+5: the kill-switch is the
   209→`revoke_delegation_on_inactivity` action (auto-trigger at 180 days); the
   210→tamper-evident log is the per-record hash chain + Merkle intervals (real-time,
   211→not 24h-delayed); the transaction value limits are the OC-201B hard_caps
   212→(₹5K/txn + ₹15K/month + ₹5K/24h); the interpretability timeline is the

   215→(§Conclusions) — our dual-control HMAC chain satisfies this by making the

   223→9 in the paper; the user reads two rows of a CSV). We built a live
   224→merchant-facing A/B: the same `/risk/score` endpoint accepts a `dataset`
   225→query param (`?dataset=amazon|olist`), branches on the param to use the

   236→### 3.3 The dual-mode (Postgres prod / file-based test) engineering pattern
   237→
   238→Paleyes 2022 §3.2 documents the "data dispersion" anti-pattern — the same
   239→entity processed by multiple services, data hard to locate, sometimes only
   240→logs. The paper's recommendation is data-oriented architectures (DOA,
   241→§8.2). Our dual-mode pattern goes further: every persistence layer supports

   245→(CI, dev laptop, prod). The pattern is NOT in Paleyes 2022 (which assumes

   247→
   248→### 3.4 The GIN expression index on `body->>'merchant_id'` for per-merchant Merkle proofs
   249→
   250→RFC 6962 Certificate Transparency specifies the Merkle tree + inclusion
   251→proof structure but doesn't address per-tenant query patterns. The Ayomide
   252→2026 §4.5.4 "Audit Trail Requirements" says "regulations require detailed
   253→trails ... for agents requires logging not just transactions but LLM
   254→reasoning that led to them" — but doesn't specify HOW a regulator queries a
   255→specific merchant's audit trail efficiently. We built a GIN index on the
   256→whole `audit_records.body` JSONB column + a functional/expression index on
   257→`(body->>'merchant_id')` so the per-merchant counts query (`WHERE
   258→body->>'merchant_id' = %s`) is an index scan instead of a seq scan past
   259→1M+ rows. This is a Postgres-specific optimization NOT in any
   260→transparency-log paper.
   261→
   262→### 3.5 The relative PR-AUC canary gate (honest for imbalanced data)
   263→
   264→Baylor 2017 TFX §5.3 specifies "quality via comparing against fixed threshold
   265→AND baseline (current production model)" — but doesn't specify which metric
   266→to use. For imbalanced data (our RTO rate 1.7%), absolute PR-AUC is
   267→misleading: a 0.10 PR-AUC on a 1.7% baseline is 6× lift (a useful model); a
   268→0.10 PR-AUC on a 50% baseline is near-random (a useless model). Our
   269→`scripts/canary_gate.py` + the `mlops.yml` model-gate job use RELATIVE
   270→PR-AUC (champion vs challenger, not absolute threshold) — the gate passes
   271→only if the challenger's PR-AUC is at least the champion's. This is the
   272→honest gate for imbalanced data; the absolute-threshold pattern in some
   273→MLOps papers would reject useful 6×-lift models. The Bahnsen 2013 paper
   274→§"Threshold opt" makes the same point ("F1-based selection ≠ cost-based
   275→selection") — we extend it to "absolute PR-AUC gate ≠ relative PR-AUC gate
   276→for imbalanced data".
   277→
   278→### 3.6 The `?dataset=olist` honest-fallback degraded-mode
   279→
   280→When the Olist bundle isn't loadable in a dev env (the data file isn't
   281→present), `?dataset=olist` returns a 503 with an honest error message
   282→("olist bundle not loadable: <reason>"), NOT a 500 (which would break the
   283→demo flow). This pattern — honest 503 with a reason string vs opaque 500 —
   284→is NOT in any paper but is the operationalization of the CBA 2026 §4.C
   285→"Operational failures: missed price windows; ... re-buys" failure-mode
   286→vocabulary. The tests in `tests/test_olist_score.py` cover the 503 path
   287→explicitly.

   291→## 4. Where We FALL SHORT (honest gaps vs literature)
   292→
   293→The user demanded brutal honesty. Here are the gaps, in priority order:
   294→
   295→### 4.1 NO model-extraction defense (Tramèr 2016 USENIX Security) — CRITICAL
   296→
   297→`docs/research/tramer_model_extraction_usenix16.pdf` (497 KB) demonstrates
   298→replicating LR/DT/SVM/NN from Google/Amazon/Microsoft prediction APIs with
   299→650-4013 queries in 70-2088 seconds. Our `models/champion/model.pkl` (124
   300→KB) and `data/olist/artifacts/model.pkl` (73 KB) are public artifacts in the
   301→repo. A competitor (or an attacker) could query `POST /risk/score` (the
   302→`score_order` action is in the `scorer` scope allowlist + requires no
   303→approval) repeatedly + distill a functionally-equivalent model. We have NO
   304→defense: no rate-limiting per-IP beyond nginx's 25r/s (which is generous),
   305→no prediction perturbation (Tramèr's recommended defense), no
   306→prediction-rounding, no RONI defense (Return Outputs, No Inputs), no
   307→prediction poisoning (Jagielski 2020). The CBA 2026 §4.C.iv "Trick fraud
   308→detection: distribute across accounts/merchants/time periods vs velocity
   309→limits; learn from blocked-transaction feedback; craft transactions"
   310→explicitly names this attack class — agents could probe our `/risk/score`
   311→to learn the model's behavior, then craft transactions that stay under the
   312→threshold.
   313→
   314→### 4.2 NO adaptive sliding-window ADWIN (Gama 2014 §3.3) — MODERATE
   315→
   316→The survey §3.3 specifies the full ADWIN checks EVERY cut point + uses
   317→EXPONENTIAL HISTOGRAMS for O(log W) memory. We check the midpoint only and
   318→use a plain `deque` (O(W) memory). Our `src/ml/drift.py:215-263` ADWIN is
   319→the "compressed" variant the survey describes in §3.3 as a pragmatic
   320→approximation ("99% as effective in practice per Bifet & Gavalda 2007 §4.2
   321→ablation" per the file docstring). The full exponential-histogram ADWIN
   322→would let us detect drift faster (every cut point vs only midpoint) with
   323→less memory (O(log W) vs O(W)). For our scale (~1k events/day per merchant)
   324→this is fine; for a 100× scale-up it becomes a bottleneck.
   325→
   326→### 4.3 NO TreeExplainer (Lundberg 2017 NeurIPS) — MODERATE
   327→
   328→We use `shap.KernelExplainer` because `HistGradientBoostingClassifier`'s
   329→internal node structure isn't exposed for the TreeSHAP recursion (the
   330→explain.py docstring `:104-108` explicitly cites this). The Hu 2025 ICCBD
   331→paper uses TreeExplainer on RF (faster + exact for tree models). The result:
   332→our SHAP explanations are ~100× slower than TreeExplainer would be +
   333→approximation vs exact. Mitigation: we cap background to 50 rows + feature
   334→dim to 100 + run inside a 5-second timeout — so the user gets SOMETHING, but
   335→the explanations are coarser than the paper's. A future fix would be to
   336→train a `RandomForestClassifier` (which IS supported by TreeExplainer) as a
   337→shadow model + use TreeExplainer on the shadow + cross-check against the
   338→HistGB predictions.
   339→
   340→### 4.4 NO transactional outbox pattern (any distributed-systems paper) — MODERATE
   341→
   342→The 002 migration docstring (`alembic/versions/002_merkle_intervals.py:30-34`)
   343→explicitly admits: "the transactional-outbox half of V3 §10.3 is deferred —
   344→Track F's fire-and-forget Redis Streams publish is the pragmatic hackathon
   345→pattern; the full outbox (audit row + outbox row in the same transaction,
   346→drained by a worker that XADDs to Redis + DELETEs the outbox row) is a
   347→Day-3+ enhancement." This means: if the process crashes BETWEEN the audit
   348→INSERT commit AND the Redis XADD publish, the audit row exists but the
   349→`risk.scores` stream event doesn't. The stream-processor won't see the
   350→event; the drift-consumer won't either; the drift feedback loop has a gap.
   351→The Mandt-Reichert outbox pattern (cited in every distributed-systems
   352→textbook) is the fix; we have the schema (the `idempotency_keys` table is
   353→the right shape) but the wiring isn't there.
   354→
   355→### 4.5 NO formal verification of the allowlist (any formal-methods agent paper) — MODERATE
   356→
   357→The SoK §5.1.1 Table 2 lists "Formal verification: Prove bounded safety
   358→properties of agent pipeline, Coverage: Broad but partial, Overhead:
   359→Infeasible." Our `check_agent_action` function has tests
   360→(`tests/test_bounded_agent.py`, 10 tests) but no TLA+/Alloy/Spin
   361→model-checker proof that the allowlist + scope→action map + dual-control
   362→HMAC chain + replay-nonce consumption together guarantee the safety property
   363→"no single-admin compromise can execute a money-moving action alone." The
   364→Ayomide 2026 §9.3 "registration ACS≥0.60 w/ certified third-party assessor;
   365→adversarial stress test vs 6 historical crisis scenarios" is the formal
   366→model the paper envisions — we have neither.
   367→
   368→### 4.6 NO human-in-the-loop threshold for the REVIEW→REJECT boundary — MODERATE
   369→
   370→The Mirabile 2026 *Trust in human-AI collaboration in finance* paper §8
   371→propositions emphasize "calibrated reliance" (under-/overreliance) — a risk
   372→officer should be able to tune the REVIEW→REJECT boundary per merchant
   373→category. Our `optimal_decision` returns `REVIEW` when `cost_review <
   374→min(cost_accept, cost_reject)` — the threshold is cost-optimal given the
   375→Bahnsen defaults (`c_fp=50`, `c_fn=600`, `c_otp=5`, `c_block=1000`,
   376→`otp_effectiveness=0.82`), NOT tunable by a risk officer per merchant. The
   377→rules engine (`src/rules/engine.py`) lets a merchant add a
   378→`amount_inr > 50000 → BLOCK` rule — but that's an additive rule on top of
   379→the BMR decision, not a per-merchant threshold override. The CBA 2026 §6
   380→"Role of Regulation" debate names this as the "outcome-oriented" vs
   381→"process-oriented" governance choice — we're process-oriented (one global
   382→model, one global threshold set).
   383→
   384→### 4.7 NO per-merchant model fine-tuning (any federated-ML paper) — MODERATE
   385→
   386→We have ONE global model for all merchants. The `?dataset=amazon|olist`
   387→switch is dataset-level, not merchant-level. A merchant selling ₹50,000
   388→electronics in pincode 560001 has a completely different RTO profile from a
   389→merchant selling ₹600 fashion in the same pincode — but they share the same
   390→champion. The Kandula 2021 DSS paper §6 conclusion explicitly recommends
   391→"build one city-level model not per-hub reduces train/test/integrate/deploy/
   392→maintain effort" — the opposite trade-off (one model for everyone) for
   393→scalability. We took the Kandula trade-off, but it means a merchant with
   394→unusual RTO patterns gets a worse fit than a per-merchant fine-tune would
   395→give. Federated learning (Shokri 2017, cited in Paleyes 2022 §4.2) is the
   396→literature answer — we have none.
   397→
   398→### 4.8 NO differential privacy (any ML-privacy paper) — LOW
   399→
   400→Shokri 2017 membership-inference attack (cited in Paleyes 2022 §4.2:
   401→"70-94% accuracy on ML-as-a-service providers") is a known risk. Our
   402→scores are deterministic — the same order through `/risk/score` returns the
   403→same probability. A membership-inference attacker could determine whether a
   404→specific order was in the training set by querying the model + comparing
   405→the score to a held-out shadow model's score. We have no DP-SGD
   406→(Abadi 2016), no PATE (Papernot 2018), no prediction rounding. The
   407→cost-curve sweep + bootstrap CIs in `/v1/policy/cost-curves` are honest
   408→about model uncertainty but NOT about membership leakage.
   409→
   410→### 4.9 NO ensemble model (Kandula 2021 DSS + SoK §5.1.2 + Bahnsen 2013) — LOW
   411→
   412→The Kandula paper compares RF/XGB/LogitBoost/ANN/CART and finds
   413→XGB+weighted-loss best for Hub-A; RF+weighted-loss best for Hub-B. The SoK
   414→§5.1.2 "Transaction Authorization Defenses" recommends "Multi-signature/
   415→threshold schemes requiring multiple signatures." The Bahnsen 2013 paper
   416→uses LR/C4.5/RF; the RF-MR A (BMR with adjusted probabilities) variant wins.
   417→We use a SINGLE HistGB champion. The deliberate trade-off: hackathon-scale
   418→simplicity (one model = one inference path = one set of explainability
   419→artifacts) vs production-grade ensembling. The `docs/RESEARCH.md` paper 1
   420→(big-data-and-analytics 2024 systematic review) explicitly names this as a
   421→limitation in our MODEL_CARD.md: "ensembles are the production-grade
   422→answer, so the single-model choice is documented as a limitation, not a
   423→hidden trade-off."
   424→
   425→### 4.10 NO rate-limiting defense against model extraction (Tramèr 2016) — LOW (subset of 4.1)
   426→
   427→Tramèr's recommended defense stack is (a) rate-limiting per-IP, (b)
   428→prediction perturbation (add small noise to the output), (c) RONI (return
   429→outputs, no inputs), (d) prediction poisoning. We have (a) at the nginx
   430→layer (25r/s per IP, generous) but NOT (b)/(c)/(d). The Tramèr paper's
   431→headline: 4,013 queries to replicate a 50-neuron NN — at 25 r/s that's
   432→~160 seconds. So our rate limit is essentially no defense.
   433→
   434→### 4.11 NO active-learning sample selection (fraud_rla_2025 + He-Garcia §3.3.4) — LOW
   435→
   436→The fraud_rla_2025 paper (committed in `docs/research/`) proposes an RL
   437→policy that picks which unlabeled transactions to send to a human for
   438→labeling, optimizing label-acquisition budget. The He-Garcia 2009 survey
   439→§3.3.4 documents the active-learning family (SVM-based active selection:
   440→pick most informative near hyperplane; Ertekin et al. LASVM online SVM).
   441→Our `LabelFeedbackService.ingest_label` is purely PASSIVE — it ingests
   442→delayed `is_returned` ground truth as it arrives, no selection. A future
   443→fix would be an active-learning policy that prioritizes labels for
   444→high-uncertainty predictions (near the cost-optimal threshold) where the
   445→label is most informative for retraining.

   449→## 5. The "Legacy + Agentic" Synthesis (the user's specific question)
   450→
   451→The user asked: *"what agentic and safety and rest systems we have built
   452→on top of a legacy system that uses both strength of legacy system and use
   453→of this agentic and safety and feedback loop"*.
   454→
   455→**The legacy layer** is the boring, proven, transactional substrate:
   456→**PostgreSQL 15 + Alembic** (transactional ACID with `SELECT FOR UPDATE`
   457→row locks for the mandate counters; 10 tables across 7 migrations with
   458→partial-unique indexes, GIN JSONB indexes, expression indexes on
   459→`body->>'merchant_id'` for per-merchant audit queries); **Redis 7 Streams**
   460→(5 named streams: `risk.scores`, `audit.records`, `cases.created`,
   461→`model.drift`, `notifications` — fire-and-forget publish with `XREADGROUP`
   462→consumer-group semantics so 3 workers — `stream-worker`,
   463→`stream-processor`, `drift-consumer` — each see all messages without
   464→competing); **FastAPI** (REST + lifespan startup hooks for in-process model
   465→loading + 24 endpoints with `Depends`-based scope enforcement); **sklearn
   466→`HistGradientBoostingClassifier`** (classical ML — not a neural net, not an
   467→LLM, just a tree ensemble with calibrated probabilities); **Merkle trees +
   468→SHA-256 hash chains** (classical cryptography from RFC 6962 Certificate
   469→Transparency — every audit record carries `raw_hash = sha256(canonical(body)
   470→+ prev_hash)`, every 1000 records OR 3600 seconds get a Merkle root chained
   471→to the previous interval's root); **HMAC-SHA256** (classical auth — the
   472→mandate token is `body.sig` where `sig = HMAC(secret, body)`; the
   473→dual-control override chains `HMAC(admin2_key, admin1_signature|canonical_body|
   474→timestamp)`); **Prometheus + Grafana + Alertmanager + Jaeger + nginx**
   475→(classical observability stack — 8-panel Grafana dashboard, 5 alert rules,
   476→OTel tracing, TLS termination, 5 security headers, rate limit 25r/s).
   477→
   478→**The agentic layer on top** adds the four bounds that make an AI agent
   479→safe to deploy in a payment system — each bound closes one of the SoK's
   480→§4.2 "Transaction Authorization" sub-vectors:
   481→
   482→- **Scope → action allowlist** (`src/api/agent_allowlist.py:65-164`) —
   483→  bounds WHAT the agent can DO. 7 actions hardcoded (`score_order`,
   484→  `request_otp`, `flag_review`, `block_order`, `upi_circle_delegated_pay`,
   485→  `validate_device_id`, `revoke_delegation_on_inactivity`). 3 scopes
   486→  (`scorer` / `ops` / `admin`) with frozenset action sets. The agent LLM
   487→  output is NEVER interpreted as instruction — only allowlisted API calls
   488→  fire. An out-of-scope action returns `403 Forbidden` with the scope-
   489→  specific message before any handler runs.
   490→- **HKDF-derived subkeys** (`src/api/keys.py:93-182`) — bounds WHICH keys
   491→  the agent can SEE. The raw admin2 key (from `RTO_ADMIN_KEYS` env var)
   492→  NEVER appears in any HMAC call — only the HKDF-derived subkey
   493→  (`salt=b"rto-override-v1"`, `info=b"dual-control"`, `length=32`) does. A
   494→  DB / memory / stack snapshot that leaks the derived key does NOT
   495→  compromise the raw admin key (the derivation is one-way — HKDF-Extract +
   496→  HKDF-Expand are both built on HMAC; recovering the IKM from the PRK or
   497→  OKM is as hard as inverting HMAC-SHA256). The salt + info tuple
   498→  domain-separates the derivation so the derived key is context-bound to
   499→  the dual-control override use case.
   500→- **Replay nonce consumption** (`alembic/versions/006_override_nonces.py`
   501→  + `src/api/routes.py:2809-2814`) — bounds WHAT the agent can REPEAT.
   502→  Each dual-control override request carries a fresh 16-byte hex nonce;
   503→  the server stores the SHA-256 HASH (not the raw nonce, so a DB
   504→  compromise doesn't leak raw nonce values). `INSERT ON CONFLICT DO
   505→  NOTHING → rowcount == 0 ⇒ 409 Conflict "replay detected"`. A captured
   506→  request can't be replayed verbatim within the 5-minute timestamp window.
   507→- **Mandate caps** (`src/api/agent_allowlist.py:71-94` hard_caps + `src/api/
   508→  mandates.py:1-1062` verify_mandate + `alembic/versions/003_mandate_
   509→  counters.py`) — bounds WHAT the agent can SPEND. All 5 OC-201B hard caps
   510→  enforced: ₹5K/txn, ₹15K/month, ₹5K 24h cooling, 5-device, 6-month
   511→  inactivity auto-revoke. Per-mandate state persisted in Postgres
   512→  (`mandate_counters` + `mandate_counter_events`) with `SELECT FOR UPDATE`
   513→  row locks so two concurrent verifies can't both read below the cap + both
   514→  decrement. The verify_mandate verdict vocabulary has 12 values so the
   515→  audit trail explains WHY a mandate was rejected.
   516→- **Dual-control co-sign** (`src/api/routes.py:2707-3010`) — bounds WHAT
   517→  the agent can DECIDE ALONE. 4-layer containment: (1) admin1 key check
   518→  (403 on fail); (2) same-key self-approve check (400 — preserves the
   519→  SoK §4.2 "Credential and Key Management" constraint that LLM-controlled
   520→  wallets cannot self-authorize); (3) replay-nonce consumption (409 on
   521→  replay); (4) HKDF-derived HMAC chain (403 on chain mismatch). The HMAC
   522→  chain binds admin2's signature to admin1's key + canonical body + ts so
   523→  a single-admin compromise cannot forge an override — admin1's key alone
   524→  is useless (no admin2 key to compute the HMAC); admin2's key alone is
   525→  useless (no admin1 signature to chain on). Both must collude OR both
   526→  must be compromised.
   527→
   528→**The feedback loop** closes the adaptation cycle the Gama 2014 survey
   529→§"Learning mode retraining/incremental/streaming" specifies + the Paleyes
   530→2022 §6.3 "Concept drift" + "Continuous delivery" recommends: **stream
   531→processor** (Track F) detects distribution shift via 4 anomaly detectors
   532→(duplicate_order_id, score_velocity_spike, score_mean_drift,
   533→hll_cardinality_spike — the last one cross-process via Redis HLL
   534→PFADD/PFCOUNT) → publishes to `model.drift` stream → **drift consumer**
   535→(Track G) drains `model.drift` with a run-length heuristic (3+ consecutive
   536→same-reason anomalies) → fires `retrain_request` → **canary gate** (mlops.yml
   537→model-gate job) runs the challenger vs champion on relative PR-AUC (honest
   538→for imbalanced data where absolute PR-AUC is misleading) + cost + slice
   539→metrics → on gate-pass, **champion swap** in `model_registry` (atomic
   540→demote of prior champion in the same transaction via the partial-unique
   541→index `ix_model_registry_single_champion`) → next `/risk/score` call loads
   542→the new champion via the lifespan → **DDM + ADWIN** reset their baselines
   543→so the new concept starts clean. The loop closes: distribution shift →
   544→detection → retrain → gate → swap → new model in production → drift
   545→detectors re-seed.
   546→
   547→This is exactly the "trustworthy agentic AI" architecture the F1000Research
   548→cross-layer review recommends: the **legacy system provides the
   549→transactional + cryptographic substrate** (Postgres ACID + Merkle + HMAC
   550→are the proven, boring, regulator-recognizable primitives); the **agentic
   551→layer adds the bounds** (allowlist + HKDF + nonce + mandate caps +
   552→dual-control = 5 bounds, each closing one SoK sub-vector); the **feedback
   553→loop closes the adaptation** (stream → drift → canary → swap → drift
   554→detectors re-seed). We are doing it the way the papers say to do it —
   555→no single paper recommends the full stack, but every layer traces to a
   556→named paper recommendation, and the COMBINATION (4-layer bounded-agent
   557→containment + dual-mode persistence + 4-detector drift feedback + Merkle
   558→audit + OC-201B hard caps) is a novel synthesis.
