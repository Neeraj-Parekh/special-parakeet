    24→## 1. Executive Summary
    25→
    26→The RTO Trust Layer is a **hackathon-grade implementation of a
    27→production-credible architecture**. The architectural primitives — Merkle
    28→audit (RFC 6962), dual-control HMAC override (RFC 5869), cost-optimal BMR
    29→(Bahnsen ICMLA 2013), bounded agent with code-enforced scope, OC-201B UPI
    30→Circle mandate caps, ONNX Runtime inference, point-in-time-correct
    31→expanding rates — are the same primitives a Razorpay-grade risk platform
    32→needs; we built them on a single Python process + Postgres + Redis where
    33→Razorpay runs Amazon MSK + Apache Flink across many services processing
    34→~5 billion events daily and 5,000–10,000 TPS. The gaps are **mostly
    35→infrastructural and bridgeable** (language/runtime, distributed
    36→streaming, real courier/ERP integrations, federated learning). One gap is
    37→**not bridgeable in a hackathon**: real Indian COD data with user history
    38→— Amazon India Kaggle has no `user_id` field, so our `user_rto_rate`
    39→feature is provably inert on the default path; we use the Olist boleto
    40→dataset (`?dataset=olist`) as the closest public proxy to demonstrate
    41→the lift.

   114→   σ=0.01 noise + 2-decimal binning raises model-extraction cost
   115→   10–100× per Tramer §6.3. Honored by env flag `ANTI_EXTRACTION_NOISE`
   116→   (default on). **Razorpay/Stripe do not publish anti-extraction noise
   117→   on their prediction APIs.**

   120→   `src/models/feature_builder.py:528` — `df.groupby(X)['rto'].shift(1).expanding().mean()`

   122→   (`expanding().mean()` without shift) is a leakage bug that ships in
